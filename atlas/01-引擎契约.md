# 01 · 引擎契约

> **读这一篇的意义**：无名杀的技能不是「写一段逻辑让它跑」，而是**向引擎注册一份声明，并遵守引擎的编译与事件契约**。
> 绝大多数「技能不发动 / 发动了没效果 / 报错 / 时好时坏」，根因都在这一层，而不在业务逻辑。
>
> 本文所有结论都标注了引擎源码位置（`resources/app/game/game.js`），可自行复核。

---

## 1. 技能住在哪：一张全局表

```js
lib.skill      // 所有技能定义，全局唯一命名空间
lib.character  // 所有武将定义
lib.translate  // 所有名字与描述文案
```

武将包通过 `game.import('character', function(lib, game, ui, get, ai, _status){ return {...} })` 返回一个包对象，引擎把其中的 `character` / `skill` / `translate` 合并进上面三张全局表。

**推论 1（最重要）**：`lib.skill` 是**扁平的全局命名空间**，没有包隔离。
两个包定义同名技能 → **加载序在后者静默覆盖前者**，不报错、不警告。
本仓库实测存在 **9 处**此类覆盖，详见 [`03-命名空间与冲突.md`](03-命名空间与冲突.md)。

**推论 2**：因为表是全局的，武将**可以合法引用定义在其他包里的技能**。
实测：包 `old` 的武将 `xin_yujin` 引用的 `jieyue` 实际定义在包 `yijiang`。这不是 bug。

**推论 3**：技能定义**不只**来自 `character/`。引擎内建（`game/game.js`）、模式专属（`mode/*.js`）、扩展（`extension/**`）都注册进同一张表。
实测：`dualside` 来自 `game/game.js:34261`，`qiwu` 来自 `mode/boss.js:8889`。
所以任何「技能缺失」的检查**必须**覆盖全来源，否则必出假阳性。

## 2. `content` 不是函数，是**被编译的状态机**

这是整个技能体系里最容易误解的一点。

你写：

```js
content:function(){
    'step 0'
    player.draw();
    'step 1'
    player.recover();
}
```

引擎实际做的事（`game.js:12070 parsex`）：

1. 取函数的**源码文本**（`func.toString()`）
2. 切掉第一个 `{` 之前的部分（**函数签名整个丢弃**）
3. 把 `'step N'` / `"step N"` 字面量**正则替换**成 `break;case N:`
4. 开头补 `switch(step){case 0:`
5. 末尾补 `if(event.step==K){event.finish();return;}`（K = 最后一个 step + 1）
6. 用 `new Function(...)` 重新构造

（`game.js:12106–12133`）

**推论 4**：`'step N'` 是**编译指令**，不是注释、不是标记。写错数字（跳号、重复）会静默错位。

**推论 5**：**函数签名被丢弃**，所以写 `content:function(event,trigger,player){...}` 与写 `content:function(){...}` 完全等价 —— 参数并非从这里来。
同理，**参数解构会炸**：`content:function({result:{bool}})` 会让第一个 `{` 落在解构上，整段代码被切错位。

**推论 6**：**不写 `'step 0'` 时**，引擎走另一条分支：在开头插入 `if(event.step==1){event.finish();return;}`（`game.js:12102`）。
这意味**单步技能可以不写 `'step 0'`**，但**写了 `'step 0'` 就必须保证 step 连续**。

**推论 7**：最后一步之后引擎**自动** `event.finish()`。所以写不写 `event.finish()` 在最后一步通常无差别 —— 但**在中间步骤里 `event.finish()` 是提前终止的唯一手段**。

**推论 7a（步骤位置硬约束）—— `'step N'` 必须写在 `content` 函数体的顶层，绝不能嵌套在任何 `{}` 块内。**
这是最容易被忽略、后果最严重的一条。

`parsex` 把 `'step N'` 换成 `break;case N:`（`game.js:12115`），而 **JavaScript 规定 `case` 标签不能出现在 `switch` 语句内嵌套的块里**。把步骤写进 `if` / `else` / `for` / `while`，替换结果直接是语法错误：

```js
switch(x){ case 0: if(y){ break; case 1: foo(); } }          // ❌ SyntaxError: Unexpected token 'case'
switch(x){ case 0: if(y){ foo(); } break; case 1: bar(); }   // ✅ 步骤在顶层
```

致命之处在于 `parsex` 有 `try/catch` 兜底（`game.js:12120–12127`）：

```js
try { new Function(copy); str=copy; skip+=...; }
catch (error) { k--; skip += result.index + result[0].length; }   // ← 静默跳过该处
```

**语法非法的那一处被直接跳过，`'step N'` 原样留下，变成惰性字符串表达式。** 后果：

- 文件照常加载，**不报任何错**
- 该步骤失去 `break`，状态机整体错位
- 若 `'step 1'` 就失败，则后续所有步骤都不会被替换，整个 `content` 退化成**单个 `case 0:` 的直线代码** —— 多步逻辑彻底崩塌

**推论 7b（跳号的真实后果 · 2026-09-13 实测补录）—— 不只是"错位"，是把整个游戏循环卡死。**

推论 4 说"跳号/重复会静默错位"，当时的语气偏轻。实测（兵权写成 0/3/4/14/16）：
替换循环**从 0 开始逐个找，遇到第一个缺失编号就 `break`**（`game.js:12106-12111`），
于是 `K` 停在断点上，末尾那句 `if(event.step==K){event.finish();return;}`
（`game.js:12129`）**永远不成立** ⇒ `event.finish()` 永不执行 ⇒ 主循环
（`game.js:41663` 起）把同一段代码**无限重复执行**，`event.step` 无上限增长：

```
实测症状：选中该武将，一进游戏就卡死，什么都点不动
诊断气泡：引擎传step=169407 event.step=169407（数字持续增长）
```

**判据**：插桩打印 `引擎传step` 与 `event.step` —— 若**持续增长**，
不必再找别的原因，先检查这个技能的步骤号是否连续。
扫描工具：`atlas/tools/renumber-steps.mjs`（报告 + `--apply` 重排并同步改写 `goto`）。
完整方法论与诊断手段的失败史见 [`../docs/内容步骤机制-踩坑与诊断方法论.md`](../docs/内容步骤机制-踩坑与诊断方法论.md)。

**正确姿势**：步骤标记一律顶格写，条件判断在每一步里重新写一遍：

```js
content: function(){
    'step 0'
    if (A) player.chooseBool('...');          // 条件写在步骤内
    'step 1'                                   // ← 顶层，合法
    if (A && result.bool) { /* 处理 */ }
    'step 2'
    if (B) player.chooseBool('...');
    'step 3'
    if (B && result.bool) { /* 处理 */ }
}
```

> 全库体检（`atlas/tools/parsex-audit.mjs`，2931 个含多步的技能）显示绝大多数技能都遵守这条约束，
> 因 `case` 非法嵌套而真编译失败的极少。完整反例见 [`04-天地归一审计.md`](04-天地归一审计.md)。

**推论 7b —— 同一个 `'step N'` 不要写两次。** `parsex` 的循环按 `k` 递增**单向**搜索，
第二个同名标记永远不会被处理，同样留下惰性字符串。因为引擎只认第一个 `case N:`，
两个动作会被合并进同一步执行 —— 通常不改变结果，但属定时炸弹（实例：`sb.js:4769` 的 `sbniepan` 有两个 `'step 3'`）。

### 2.0 两条铁律（实证得来，代价最大）

#### 铁律一 · `content` 一律写**普通函数**，绝不写 generator

`parsex` 有**两条完全不同的分支**，取决于 `localStorage.finalParsex`：

| 分支 | 触发条件 | 位置 | 对 generator 的处理 |
|---|---|---|---|
| `old` | `finalParsex == 'old'`（UI 里的**「疾速模式」**） | `game.js:12072-12090` | **无 generator 检测、无 `try/catch`** — 纯正则切 `'step N'` |
| else | 其他一切情况 | `game.js:12091-12189` | 有 `gnc.isGeneratorFunc` 分支 + `Legacy()` 包装 + `try/catch` |

在 `old` 分支下，generator 的签名形如 `function* (event, { player })`，
按「切掉第一个 `{` 之前」的规则会把 `{ player }` 的解构当成函数体开头 → **硬语法错误，
而这分支没有 try/catch 兜底 → 直接抛 `SyntaxError: Unexpected token ')'`**。

**结论：`content: function () {...}`，永远不要 `function*`、不要参数解构。**
写普通函数在**两条分支下都能编**，是唯一稳的选择。
（实测回归：`atlas/tools/verify-extension.mjs` 会分别按两条分支试编，要求都是 0 失败。）

#### 铁律二 · `content` 里**读不到外层闭包变量**

`game.js:12131` 用 `new Function(...)` 重建函数 —— 它在**全局作用域**里求值。
于是 `game.import('character', function(){ var helper = ...; ... })` 这类
**包级闭包在 `content` 内部一律是 `undefined`**（运行时报 `ReferenceError`）。

```js
// ❌ 运行时 ReferenceError: findCeTarget is not defined
content: function(){ var ce = findCeTarget(); ... }
// ✅ 就地展开
content: function(){
    var ce = null;
    for (var i = 0; i < game.players.length; i++)
        if (game.players[i].hasMark('mgj_ce')) { ce = game.players[i]; break; }
}
```

**哪些字段受此约束？** 只有被 `parsex` 编译的那三个：**`content` / `cost` / `onremove` 一类的
函数体字段**。`filter` / `check` / `ai` / `init` 等**直接当普通函数调用、不经过 `new Function`**，
闭包**完好**，可以放心用辅助函数。

所以常见搭配是：`filter` 里用闭包 helper 写得很干净，`content` 里把同一段逻辑内联展开。

### 2.0.1 各步骤之间不共享局部变量

每个 `'step N'` 都是**独立编译出来的函数体**，不是同一个函数里的顺序代码块。
`'step 0'` 里的 `var x` 在 `'step 1'` 里**不存在**。

跨步传值只有一条路：**挂到 `event` 上**。

```js
'step 0'
var keys = ['a','b'];
event.mgjKeys = keys;          // ← 存到 event
'step 1'
var k = event.mgjKeys[0];      // ← 从 event 取
```

（`stepHead` 里声明的变量看似"提前"，实则是每步各自重算一遍，同样不能跨步。）

### 2.1 十九个注入变量

每次执行一步前，引擎刷新这些变量并作为实参传入（`game.js:41666–41676`，调用点 `game.js:41790`）：

```js
var source  = event.source;
var player  = event.player;
var target  = event.target;
var targets = event.targets;
var card    = event.card;
var cards   = event.cards;
var trigger = event._trigger;   // 触发源事件
var result  = event._result;    // 上一次选择的返回值
// 另加：event, step, skill, forced, num, _status, lib, game, ui, get, ai
```

| 变量 | 含义 | 关键约束 |
|---|---|---|
| `player` | 事件主体 | 对技能事件 = 技能拥有者 |
| `target` | 单目标 | **每步重新读 `event.target`**。第 1 步选了目标，第 2 步想用 `target` 必须**手动写回 `event.target = target`** |
| `cards` | 事件牌集 | = `event.cards`，即**本事件自己的字段**，不是「当前处理的所有牌」 |
| `trigger` | 触发源 | 只在触发技里有值；主动技为 `undefined` |
| `result` | 上一步结果 | 主动技/无选择的步骤里为 `undefined` |

**推论 8**：`target` 不跨步自动保留。这是新手最常踩的坑，正确写法是显式 `event.target = result.targets[0]`。

**推论 9**：`result` 只在**存在上一步选择**时有定义。直接读 `result.bool` 而不判空，会在「AI 直接跳过选择」等路径上抛错。

### 2.2 步进控制

| 写法 | 引擎实现 | 效果 |
|---|---|---|
| `event.finish()` | — | 立即终止整个事件 |
| `event.goto(n)` | `this.step = n - 1`（`game.js:31959`） | 跳回第 n 步；配合末尾 `step++` 净效果为「下一步执行 n」 |
| `event.redo()` | `this.step--`（`game.js:31962`） | 重跑当前步（实现循环） |
| `event.getParent(n)` | 向上 n 层（`game.js:32036`） | `n=1` 是父事件 |
| `event.getParent('名字')` | 沿 parent 链按 `name` 上溯 | 用于跨层找回「本次发动事件」 |

**推论 10**：`redo()` 必须打在**正确的层级**上。在子事件回调里 `redo()` 只会重跑回调自身，形成死循环；要重跑主技能必须 `event.getParent(2).redo()`。

## 3. 事件与触发时机

引擎主循环每轮推进 `event._triggered` 计数（`game.js:41747–41764`），依次派发：

```
<事件名>Before  →  <事件名>Begin  →  （结算主体）  →  <事件名>End  →  <事件名>After
```

技能用 `trigger` 声明挂载点：

```js
trigger:{ player: 'phaseZhunbeiBegin' }   // 自己回合准备阶段「开始时」
trigger:{ global: 'damageBegin' }         // 全局：任何人造成伤害前
trigger:{ source: 'damageBegin' }         // 自己为伤害来源时
trigger:{ target: 'useCardToTargeted' }   // 自己成为牌的目标时
```

**推论 11**：`Begin` / `Before` 段**可以取消**（`.cancel()`），`End` / `After` 段**不能**。想在结算前干预必须挂在 `Begin`/`Before`。
实测样例见范式库 A6（`jiange:lingfeng` 用 `phaseDrawBefore` + `trigger.cancel()` 替换摸牌）。

**推论 12**：触发技的 `content` 里能通过 `trigger.xxx` 读到**触发源事件的字段**。
这是「追加目标 / 改伤害 / 改结算参数」类技能的唯一入口 —— 你改的不是技能，是**正在结算的那个事件**。

### 3.1 `filter` 与 `check` 的分工（高频误用）

| 字段 | 作用 | 人类玩家 | AI |
|---|---|---|---|
| `filter(event, player)` | **硬门槛**：返回 false 则技能**不点亮、不询问** | 不可用 | 不可用 |
| `check(event, player)` | **AI 决策**：只影响 AI 是否选择发动 | **仍会被询问** | 按返回值决定 |
| `ai: { order, result }` | AI 出牌阶段的优先度与收益评估 | 无影响 | 影响排序 |

**推论 13**：把「AI 想不想发动」写进 `filter` 是**错误**的 —— 那会让人类玩家也无法发动。
实测对照：`jiange:lingfeng` 用 `check`（正确，人类可自选），`swd:lingfeng` 用 `filter`（硬门槛，因它有明确数值条件）。见范式库 A7。

## 4. 声明式字段速查

这些字段**不产生逻辑**，只是给引擎的注册指令，但错一个就整个技能不生效。

| 字段 | 作用 | 引擎位置 |
|---|---|---|
| `group: 'x'` / `['x','y']` | **把成员技能的触发器挂到本技能名下**。成员**不必**写进武将数组 | `game.js:27808`（加）/ `28539`（删） |
| `subSkill: { mark: {...} }` | 自动派生 `父技能_mark`，强制 `sub=true`，翻译继承父技能 | `game.js:44153` |
| `inherit: 'x'` | 复用 x 的字段，**本对象里显式写的覆盖之** | — |
| `limited: true` | 限定技；引擎自动补 `intro.content='limited'`、`skillAnimation=true`、`init` 初始化 storage | `game.js:44148` |
| `juexingji: true` | 觉醒技**标签**（供检索/排除）。**不等于**退役 —— 退役要调 `awakenSkill()` | — |
| `forced: true` | 强制发动，跳过询问 | — |
| `direct: true` | 发动时不弹技能名 | — |
| `locked: true` | 不播技能动画/配音（与 `forced` 无关，别混用） | — |
| `charlotte: true` | 隐藏技能，不进技能表（子技能、状态位常用） | — |
| `unique` / `gainable` | 参与「获得技能」体系，可被夺取/复制 | — |
| `derivation: 'x'` | 声明衍生技，供展示与 AI 认知 | — |
| `mod: { ... }` | **改写引擎规则查询**（不产生事件，纯查询期干预），如 `ignoredHandcard` / `cardDiscardable` | — |
| `global: 'x'` | 给全场玩家挂载技能 | — |
| `shaRelated: true` | 声明与【杀】相关，影响 AI 与牌堆查询 | — |

**推论 14**：`group` 与「武将数组里列出成员」**是两种不同机制**，不要混用。
用 `group` 时成员只作为**触发器载体**，其 `content` 仍会执行，但**不会**在技能框里单独显示。
实测：`standard:lvbu` 的技能数组只有 `['wushuang']`，而 `wushuang1`/`wushuang2` 通过 `group` 挂入 —— 这就是它们显示「无直接引用」的原因。

**推论 15**：`juexingji: true` 与 `awakenSkill()` 是**两件事**。
前者是标签（让检索型技能能找到它），后者是执行退役（从技能表移除 + 写入 `awakenedSkills`）。
只写前者不调后者 → 觉醒技可反复发动；只调后者不写前者 → 检索型技能找不到它。

## 5. 文案契约

`translate` 是**单数**（不是 `translates`），且名字与描述**必须成对**：

```js
translate: {
    myskill:      '技能名',
    myskill_info: '技能描述。',
}
```

**推论 16**：只写 `myskill` 不写 `myskill_info` → 技能框描述空白；只写 `_info` 不写名字 → 技能框标题空白。
两者都是**静默失败**（不报错）。

**推论 17**：`characterTitle` 用 `#y` / `#g` / `#r` 等前缀控制称号颜色。
`characterIntro` 缺失时图鉴简介为空（不报错）。

### 6.1 处理区与「不置入弃牌堆」

判定牌/拼点牌默认会进入**处理区**（`ui.ordering`），随后由 `orderingDiscard` 统一弃掉：

```js
// game.js:14558  cardsGotoOrdering
evt.orderingCards.addArray(cards);                       // 登记
game.createEvent('orderingDiscard', false, evt.getParent());

// game.js:14551  orderingDiscard
// 只弃掉「仍在处理区(position=='o')」的登记牌
```

**推论 18**：想让判定牌/拼点牌**留在处理区**，唯一手段是从 `evt.orderingCards` 里 `remove()` 掉它。
实测样例：`extra:reshuishi`（慧识）在 judge 的 callback 里做 `event.getParent().orderingCards.remove(event.judgeResult.card)`，随后用 `cards.filterInD()`（缺省筛 `position=='o'`，`game.js:9083`）把这些牌收割出来。

## 7. 最小正确骨架

把上面所有契约压成一个可以直接照抄的模板：

```js
myskill:{
    // ── 1. 注册层：决定"能不能发动"
    trigger:{ player: 'phaseZhunbeiBegin' },   // 或 enable:'phaseUse'
    forced: false,                              // 需询问则 false
    usable: 1,                                  // 出牌阶段限一次
    filter: function(event, player){            // 硬门槛（人类也不可用）
        return player.countCards('h') > 0;
    },
    check: function(event, player){             // 仅 AI 决策（人类仍会被询问）
        return true;
    },

    // ── 2. 逻辑层：状态机
    content: function(){
        'step 0'
        player.chooseTarget('选择一名角色').set('ai', function(target){
            return get.attitude(_status.event.player, target);
        });
        'step 1'
        if(!result.bool){ event.finish(); return; }   // 结果判空，别直接读 result.bool
        var t = result.targets[0];
        event.target = t;                             // ★ 写回，下一步才能用 target
        t.draw(2);
    },

    // ── 3. 文案层：必须成对
    // translate 里补 myskill / myskill_info

    // ── 4. AI 层
    ai:{ order: 5, result:{ player: 1 } },
},
```

- [ ] `translate` 里 `名` 与 `_info` **都写了**

- [ ] 每个读 `result.xxx` 的地方都**先判空**
- [ ] 跨步使用 `target` 前**已写回 `event.target`**
- [ ] `juexingji` / `limited` 技能**都调了** `awakenSkill()`
- [ ] `group` 成员与武将数组**没有重复列**
