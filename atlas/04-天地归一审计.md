## B1 · `mgj_zhuce` 编译失败（最严重）

### 现象

`content`（137–191 行）把步骤标记写进了 `if / else` 块内部：

```js
138 |  var ce = findCeTarget();
139 |  'step 0'
140 |  if (!ce) { event.finish(); return; }
142 |  if (ce.countMark('mgj_picked1') < 1) {
143 |      player.chooseBool('给「策」添加效果【回复体力】（限一次）？')...
144 |      'step 1'          // ← 在 if 块内
145 |      if (result.bool) { ... }
150 |      'step 2'          // ← 在 if 块内
151 |  } else {
152 |      'step 1'          // ← 在 else 块内
153 |      'step 2'
154 |  }
156 |  if (ce.countMark('mgj_picked2') < 1) {
157 |      player.chooseBool(...)
158 |      'step 3'          // ← 在 if 块内
        ... 同理直到 'step 7'
```

### 机制

`parsex` 把 `'step N'` 替换成 `break;case N:`（`game.js:12115`）。而 **JavaScript 不允许 `case` 标签出现在 `switch` 语句内嵌套的块里**：

```js
switch(x){ case 0: if(y){ break; case 1: foo(); } }   // ❌ SyntaxError: Unexpected token 'case'
```

`parsex` 有 `try/catch` 兜底（`game.js:12120–12127`），语法非法时**静默跳过该处**：

```js
catch(error){ k--; skip += result.index + result[0].length; }
```

### 实测证据

`atlas/tools/parsex-probe.mjs` 把引擎的 `parsex` 算法原样抽出跑了一遍：

```
k=0: 在偏移 42 处替换 'step 0' -> switch(step){case 0:
k=1: 在偏移 257 处替换 'step 1' -> break;case 1:
      语法非法，跳过该处：Unexpected token 'case'
k=1: 在偏移 479 处替换 'step 1' -> break;case 1:
      语法非法，跳过该处：Unexpected token 'case'
k=1: 未找到 -> break (最终 K=1)

剩余未被替换的 step 字面量：'step 1', 'step 2', 'step 1', 'step 2',
  'step 3', 'step 4', 'step 3', 'step 4', 'step 5', 'step 6', 'step 5', 'step 6', 'step 7'
```

**`k=1` 就断了，`K=1`，13 个 step 全部残留为惰性字符串。**

全库对照（`parsex-audit.mjs`，2931 个含多步的技能）：因 `case` 非法嵌套而失败的，**只有这一处**。

### 后果

`content` 编译后退化为**单个 `case 0:` 的直线代码**。执行顺序变成：

```
ce = findCeTarget()
if(A){ chooseBool1 }      ← 只创建事件，不等待
if(result.bool){ 加效果1 } ← 读到的 result 还是初值 {}
if(B){ chooseBool2 }
if(result.bool){ 加效果2 } ← 同上
if(C){ chooseBool3 }
if(result.bool){ 加效果3 }
chooseBool4
if(result.bool){ 加效果4 }
```

`event._result` 的初值是 `{}`（`game.js:40343`），所以 `result.bool` 是 `undefined` → 不抛错、全部走假分支。

**净效果**：

1. **四个效果一个也不会被添加** —— 四个 `chooseBool` 都是在同一 step 内创建的，而它们的 `if(result.bool)` 处理器**在结果产生之前就已执行完毕**
2. **每回合固定弹出 4 次询问**（原来应是 1–4 次条件性询问）
3. 引擎**不报任何错**，玩家只会觉得「铸策点了没反应」

> 这与作者心得 §5「content 里 4 个 chooseBool 依次添加效果」的描述**不符** —— 实际一次也没成功添加过。

### 正确写法

步骤标记一律顶格，条件在每一步内重复：

```js
content: function () {
    var ce = findCeTarget();
    'step 0'
    if (!ce) { event.finish(); return; }
    if (ce.countMark('mgj_picked1') < 1) {
        player.chooseBool('给「策」添加效果【回复体力】（限一次）？')...
    }
    'step 1'
    if (ce.countMark('mgj_picked1') < 1 && result.bool) {
        ce.addMark('mgj_eff1', 1);
        ce.addMark('mgj_picked1', 1);
        game.log(player, '给「策」添加了效果', '#g【回复体力】');
    }
    'step 2'
    if (ce.countMark('mgj_picked2') < 1) {
        player.chooseBool('...【额外执行一个出牌阶段】...')...
    }
    'step 3'
    if (ce.countMark('mgj_picked2') < 1 && result.bool) { ... }
    // ... 效果3、效果4 同理
}
```

要点：**条件在两个步骤里各写一次**（step N 决定要不要问，step N+1 决定要不要落实），这是引擎约束逼出来的固定模式。

## B2 · `mgj_nohurt` 的 `filter` 恒为 false

### 代码

```js
96 |  trigger: { global: 'damageBegin' },
97 |  filter: function (event) {
98 |      var source = get.player(event.source);
99 |      var target = get.player(event.player);
100 |     if (!source || !target) return false;
101 |     if (isSoul(source) && target.hasMark('mgj_ce')) return true;
102 |     if (isSoul(target) && source.hasMark('mgj_ce')) return true;
103 |     return false;
104 | },
```

### 机制

`get.player` **不接受任何参数**（`game.js:62081–62083`）：

```js
player:function(){
    return _status.event.player;
},
```

传进去的 `event.source` / `event.player` 被**完全忽略**，两次调用返回**同一个对象**。

于是 `source === target === X`，两行判定塌缩成同一个条件：

```js
isSoul(X) && X.hasMark('mgj_ce')
```

- 若 `X` 是谋郭嘉（技能拥有者）：`isSoul` 为真，但**谋郭嘉身上没有「策」标记**（`mgj_ce` 在定策选中的目标身上）→ false
- 若 `X` 是伤害承受者：只有承受者恰好是谋郭嘉时才可能为真 → 同上仍 false；否则 `isSoul` 即为 false

**两种情况都返回 false —— 相互免伤从未生效过一次。**

### 正确写法

直接使用事件字段，不要经过 `get.player()`：

```js
filter: function (event) {
    var source = event.source, target = event.player;
    if (!source || !target) return false;
    if (source.hasSkill('mgj_dingce') && target.hasMark('mgj_ce')) return true;
    if (target.hasSkill('mgj_dingce') && source.hasMark('mgj_ce')) return true;
    return false;
},
```

## B3 · `mgj_nohurt` 的 `event.cancel()` 取消了错误的事件

### 代码

```js
105 |  content: function () {
106 |      event.cancel();
107 |  },
```

### 机制

触发技的 `content` **运行在一个新建的事件里**，触发源另存为 `_trigger`（`game.js:15552–15555`）：

```js
next.player = player;
next._trigger = trigger;        // ← 触发源单独存放
next.triggername = event.triggername;
next.setContent(info.content);
```

所以 `content` 内部：`event` 是**技能自身的事件**，`trigger` 才是**伤害事件**。

`cancel()` 的实现（`game.js:31939–31945`）：

```js
cancel:function(arg1,arg2,notrigger){
    this.untrigger(arg1,arg2);
    this.finish();
    if(notrigger!='notrigger'){ this.trigger(this.name+'Cancelled'); ... }
},
```

它只作用于**被调用的那个事件自身**。`event.cancel()` 只是把 `mgj_nohurt` 这个技能事件收尾，**伤害照常结算**。

### 自相矛盾的铁证

同一个文件里的 `mgj_skip` 用的是**正确**写法：

```js
254 |  content: function () {
255 |      trigger.cancel();       // ← 正确：取消触发源事件
256 |      player.removeMark('mgj_eff4_perm', 1);
```

两处写法不一致，说明作者对 `event` / `trigger` 的分工没有形成稳定认知。

### 正确写法

```js
content: function () {
    trigger.cancel();
},
```

## B4 · 四个铸策效果技能的判定主体错位

### 代码（四个技能同构）

```js
194 | mgj_eff1: {
198 |   trigger: { player: 'phaseBegin' },
199 |   filter: function (event, player) {
200 |     return player.hasMark('mgj_ce') && player.countMark('mgj_eff1') > 0;
201 |   },
202 |   content: function () {
203 |     if (player.countMark('mgj_eff1') > 0) {
204 |       player.recover(1);
```

```js
212 | mgj_extra_phase: trigger:{player:'phaseBegin'},      filter: player.hasMark('mgj_ce') && ...
229 | mgj_boost:       trigger:{source:'damageBegin'},    filter: player.hasMark('mgj_ce') && ...
246 | mgj_skip:        trigger:{player:'phaseDiscardBefore'}, filter: player.hasMark('mgj_ce') && ...
```

### 机制

| 事实 | 依据 |
|---|---|
| 四个技能**都属于谋郭嘉** | 武将数组 `mouguojia_soul: [..., [ 'mgj_dingce','mgj_zhuce','mgj_lixue','mgj_nohurt','mgj_ce_remove','mgj_eff1','mgj_extra_phase','mgj_boost','mgj_skip' ]]`（34–38 行） |
| filter 里的 `player` = **技能拥有者** = 谋郭嘉 | 引擎传参约定 |
| `mgj_ce` 标记在**「策」持有者**身上 | 定策 76 行 `target.addMark('mgj_ce', 1)` |
| `mgj_eff*` 标记也在**持有者**身上 | 铸策 146/160/174/187 行 `ce.addMark(...)`，`ce = findCeTarget()` |
| 定策**没有**把技能授予持有者 | 68–89 行只做 `addMark`，无 `target.addSkill(...)` |

于是：**谋郭嘉身上既没有 `mgj_ce`，也没有 `mgj_eff*`** → `player.hasMark('mgj_ce')` 恒为 false → **四个效果全部永不发动**。

> 顺带一提：四个触发视角也错了。`{player:'phaseBegin'}` 是**谋郭嘉**的回合开始，而效果应当作用于**「策」持有者**的回合；`{source:'damageBegin'}` 是谋郭嘉为伤害来源，而效果③应作用于持有者造成的伤害。

### 正确写法（二选一）

**方案 A（推荐，改动最小）：技能留在谋郭嘉身上，改为监听全场，并用 `trigger.player` 指代持有者**

```js
mgj_eff1: {
    forced: true, sub: true, popup: false,
    trigger: { global: 'phaseBegin' },
    filter: function (event, player) {
        var ce = findCeTarget();
        return ce != null && event.player == ce && ce.countMark('mgj_eff1') > 0;
    },
    content: function () {
        var ce = findCeTarget();
        if (!ce) return;
        ce.recover(1);
        ce.removeMark('mgj_eff1', 1);
        game.log(ce, '消耗了「策」效果', '#g【回复体力】');
    },
},
```

同类改写：

| 技能 | trigger | 作用于 |
|---|---|---|
| `mgj_eff1` | `{ global: 'phaseBegin' }` | `trigger.player`（持有者回合开始）回复体力 |
| `mgj_extra_phase` | `{ global: 'phaseBegin' }` | 给 `trigger.player` 插入额外出牌阶段 |
| `mgj_boost` | `{ global: 'damageBegin' }` | `trigger.source` 是持有者时伤害 +1 |
| `mgj_skip` | `{ global: 'phaseDiscardBefore' }` | `trigger.player` 是持有者时取消弃牌阶段 |

**方案 B：在定策里把技能授予持有者**

```js
// mgj_dingce content step 1 内
target.addSkill(['mgj_eff1', 'mgj_extra_phase', 'mgj_boost', 'mgj_skip']);
```

此时四个 filter 原样即可工作（`player` 就是持有者）。代价：四个技能的 `forced/sub/popup` 语义要在被授予者身上重新审视，且死亡时需清理。

## B5 · `mgj_boost` 改错了字段

### 代码

```js
241 |  content: function () {
242 |      event.damage += 1;
243 |  },
```

### 机制

引擎的**伤害值字段是 `event.num`**：

- `game.js:41674` —— 注入变量 `var num = event.num;`
- `damage` 事件的 content（`game.js:20755` 起）**全程使用裸变量 `num`**，最终 `player.changeHp(-num, false)`（`20830`）
- 全库惯例为 `trigger.num++` / `event.num = ...`（34 个武将包共 **658 处**）

而 **`event.damage` 在 `game.js` 里出现 0 次**；在整个 `character/` 目录里只出现 1 次（`extra.js:13256`），且那处是 `event.damage = ... == 1` 的**布尔自定义字段**，与伤害值无关。

`event.damage += 1` 在 `undefined` 上做加法得到 `NaN`，写进一个引擎从不读取的字段 → **完全空操作**。
即使 B4 修好让技能能触发，这行仍然是没用的。

### 正确写法

```js
content: function () {
    trigger.num += 1;
},
```

**参考**：本包其他技能改伤害都是用 `trigger.` 前缀（如 `mtg.js:458` `trigger.num += player.storage.msilian-2`），作者心得 §4.8 写的「`event.damage` 修改」本身就是错的记录。

## B6 · `mgj_lixue` 漏掉「失去体力」

### 代码

```js
262 | mgj_lixue: {
263 |   forced: true,
264 |   trigger: { player: ['damageEnd', 'recover'] },
265 |   filter: function (event, player) {
266 |     return findCeTarget() != null;
267 |   },
```

### 机制

**`loseHp` 是独立事件，与 `damage` 不同**（`game.js:26455`）：

```js
loseHp:function(num){
    var next=game.createEvent('loseHp');
    ...
    next.setContent('loseHp');
```

「失去体力」（`player.loseHp(n)`）不产生 `damage` 事件，因此 `damageEnd` 不会触发。
卡面写的是「**当你体力值发生变动时**」，而当前实现只覆盖了「受伤」与「回复」。

### 正确写法

```js
trigger: { player: ['damageEnd', 'recover', 'loseHpEnd'] },
```

> 若还要覆盖 `changeHp` 直接改体力的极端情况，需额外挂 `changeHp` 相关事件，但 `loseHpEnd` 是当前最明确的一处遗漏。

## B7–B10 · 轻微与提示

### B7 `mgj_ce_bound` 是裸标记

```js
77 |  player.addMark('mgj_ce_bound', 1);
```

`lib.skill['mgj_ce_bound']` 不存在 → `markSkill` 取不到 `intro`（`game.js:23821` 要求 `lib.skill[i].intro`）→ 标记无图标、无文案。
**建议**：改用 `player.storage.mgj_ce_bound = true;`（纯状态，不需要显示）。

### B8 效果④的命名与限次

```js
183 |  // 效果4：跳过一次弃牌阶段
184 |  player.chooseBool('给「策」添加效果【跳过一次弃牌阶段】？')...
187 |      ce.addMark('mgj_eff4_perm', 1);      // ← 名字带 _perm（永久）
...
256 |      player.removeMark('mgj_eff4_perm', 1);   // ← 却会被消耗掉
```

- 命名含 `_perm` 但实际是消耗品 → 改名 `mgj_eff4` 更准确
- 效果④**没有** `mgj_picked4` 守卫（对比效果①②③），因此每回合都能再叠一层
- `ceX()`（22–26 行）把 `mgj_eff4_perm` 计入 X → **沥血摸牌数会随回合线性膨胀**

若这是刻意设计（越拖越强），建议在卡面写明；若不是，补一个限次守卫。

### B9 `mgj_ce_remove` 在死亡事件内交互

```js
113 |  trigger: { player: 'die' },
121 |  player.chooseBool('是否移除「策」标记？')...
```

在 `die` 事件中向即将离场的玩家索取输入。单机可用，但在多段死亡链（濒死→救回→再死）或联机回放场景下，交互时机不稳。
更稳的做法是挂 `dieAfter`，或改为无交互的自动结算。

### B10 `var ce` 每步重算

```js
138 |  var ce = findCeTarget();
139 |  'step 0'
```

在 `parsex` 语义下，`switch` 之前的代码**每一步重入都会执行** —— 这里恰好是必要的（`ce` 需跨步可用）。
但如果「策」持有者在技能结算途中死亡或易主，后续步骤会切到新目标。属可接受的潜在时序问题，建议在每步开头补 `if (!ce) { event.finish(); return; }`。

```bash
# 提交任何技能前，先过 01-引擎契约.md 末尾的照抄清单
```

**本清单里 B1–B5 全部属于「引擎不报错、技能静默失效」类型** —— 这正是 [`01-引擎契约.md`](01-引擎契约.md) 反复强调的那类失败：
**无名杀不会告诉你技能写错了，它只会安静地什么都不做。**
