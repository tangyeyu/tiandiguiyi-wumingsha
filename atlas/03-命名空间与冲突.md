# 03 · 命名空间与冲突

> 本文是**实测报告**，不是理论推演。数据由 `atlas/tools/check-collisions.mjs` 对 34 个武将包 / 5227 个技能定义扫描得出，
> 完整原始表格见 [`index/collisions.md`](index/collisions.md)。

---

## 1. 为什么这件事致命

```js
lib.skill      // 所有技能，一张扁平表
lib.character  // 所有武将，一张扁平表
```

包与包之间**没有命名空间隔离**。引擎在 `game.js:9786-9791` 把各包内容合并进同一张表：

```js
var pack = window.noname_package;
for (i in pack.character) { ... lib.config.all.characters.push(i); }
```

随后按该数组顺序逐个加载包文件（`game.js:10029`）：

```js
lib.init.js(`${lib.assetURL}character`, lib.config.all.characters, packLoaded, packLoaded);
```

**先加载的定义被后加载的同名定义覆盖 —— 不报错、不警告、不记录。**

表现为：「某个武将的技能莫名其妙不对」，而不是「启动失败」。这类 bug 几乎不可能靠读单个包发现。

## 3. 九处技能名重复

| 技能名 | 定义 A | 定义 B |
|---|---|---|
| `iwasawa_refenyin` | `diy` `diy.js:10443` | `xianding` `xianding.js:10110` |
| `iwasawa_fenyin` | `diy` `diy.js:10509` | `xianding` `xianding.js:10176` |
| `junkyuheng` | `diy` `diy.js:17842` | `extra` `extra.js:12859` |
| `junkdili` | `diy` `diy.js:17890` | `extra` `extra.js:12907` |
| `junkshengzhi` | `diy` `diy.js:17962` | `extra` `extra.js:12979` |
| `junkquandao` | `diy` `diy.js:17999` | `extra` `extra.js:13016` |
| `junkchigang` | `diy` `diy.js:18022` | `extra` `extra.js:13039` |
| `zhimeng` | `extra` `extra.js:2818` | `xianjian` `xianjian.js:3865` |
| `lingfeng` | `jiange` `jiange.js:248` | `swd` `swd.js:1473` |

**注意 `junk*` 那一组有 5 个**：这不是偶然重名，而是 `diy` 包**整组复制**了 `extra` 包的「神孙权」技能族（`junkyuheng` / `junkdili` / `junkshengzhi` / `junkquandao` / `junkchigang` —— 对应 `extra.js:12859-13039` 的连续区间）。
无论加载序如何，**必有一组的实现被整族覆盖**。

### 3.1 最直观的一对：`lingfeng`

两个 `lingfeng` 是**完全不同的技能**：

| | `jiange:lingfeng` (`jiange.js:248`) | `swd:lingfeng` (`swd.js:1473`) |
|---|---|---|
| 武将 | `jg_liubei` | `swd_huiyan` |
| 触发 | `phaseDrawBefore`（摸牌阶段前） | `phaseEnd`（回合结束） |
| 效果 | 取消摸牌，改为亮 2 张牌；异色则可弃他人 1 牌，最后收下这 2 张 | 使用牌数 ≥ min(3,体力) 时，对攻击范围内一人造成 1 伤害，或取消并获得 1 护甲 |
| AI 门槛 | `check` | `filter` |

**后果**：若 `swd` 后加载，则 `jg_liubei` 的「凌锋」变成回合结束的伤害技 —— **摸牌阶段不再被替换**，AI 与人类都会按错误规则行动；反之 `swd_huiyan` 的技能被换成摸牌版。
**两个武将，必然有一个是错的。**

### 3.2 为什么不能简单地「确认谁赢就完事」

我尝试静态确定覆盖胜者，结论是**做不到**，理由如下：

1. `lib.config.all.characters` 的初始键序来自 `game/package.js:2-24`，其中只声明了 **21 个**包：

   ```
   standard, extra, old, mobile, shiji, sb, collab, shenhua, yijiang, refresh,
   sp, xinghuoliaoyuan, yingbian, clan, huicui, xianding, sp2, tw, offline, jsrg, ddd
   ```

2. 但 `character/` 目录下实有 **34 个**包文件。`diy`、`xianjian`、`jiange`、`swd` 等**均不在**上述 21 个之内，
   说明它们由运行期机制追加。

3. 扩展确实会追加（实例）：
   - `extension/雷霆万钧/extension.js:8960` → `lib.config.all.characters.push('thunder')`
   - `extension/天地归一/extension.js:282` → `lib.config.all.characters.push('tiandiguiyi')`
   - `extension/手杀ui/fonts/extension.js:4864` → 循环 `push(i)`

4. 而 `game/config.js:23` 的白名单**包含** `diy`：

   ```js
   sgscharacters:['standard','shenhua','xinghuoliaoyuan','refresh','yijiang','sp','sp2',
                  'xianding','huicui','extra','old','mobile','shiji','tw','yingbian',
                  'offline','jsrg','sb','clan','collab','diy']
   ```

   → 该发行版**预期** `diy` 会被加载，但 `package.js` 未声明它，两者的矛盾印证了加载路径被发行版改动过。

**结论：9 处冲突的「胜者」无法仅凭仓库静态确定，且可能随用户启用的扩展组合而变。**

因此正确处理方式是**改名**，而不是"查明谁赢然后接受它"。

### 3.3 改名方案（保持行为不变，且向后兼容）

不能简单改名 —— 因为武将数组里引用的就是旧名。安全做法是**给冲突技能起限定名，并在武将数组里同步改**：

```js
// swd.js —— 改名
swd_lingfeng:{
    // ... 原 lingfeng 的内容，一字不改
}

// swd 包里该武将的数组同步改
swd_huiyan:['male','wu',4,['swd_lingfeng', ...]],
```

若该技能**已经**被玩家存档/录像引用，则需保留旧名做别名（`inherit` 转发）：

```js
lingfeng:{ inherit:'swd_lingfeng' },
```

**推荐命名规范**（避免未来冲突）：

| 场景 | 规范 | 例 |
|---|---|---|
| 同一武将包内 | 包名前缀 + 语义 | `swd_lingfeng`、`junk_dili` |
| 武将专属同名技 | 武将 id 前缀 | `sbdujiang`、`junkdili` |
| 子技能/状态位 | 父技能名 + `_` + 用途 | `resghuishi_mark`、`dddfusi_refused` |
| 从别包借用的实现 | **不要复制**，用 `inherit` | `inherit:'zhenlue'` |

**关键**：`junk*` 那组的问题根源就是**复制粘贴**而非 `inherit`。
若 `diy` 包改为 `inherit:'junkyuheng'`，则既复用实现又**不产生同名定义**，冲突自然消失。

## 4. 一处真悬空引用

| 缺失技能名 | 引用武将 | 位置 |
|---|---|---|
| `zuijian` | `xk_fujianhan` | `xiake.js:10` |

原文（`xiake.js:10`）：

```js
xk_fujianhan:['male','qun',4,['zuijian','zitong']],
```

`zuijian` 在**全库**（含 `game/`、`mode/`、`extension/`，补充扫描 303 个 js/ts 文件）都没有定义。

**后果**：
- 该技能**永远不会发动**（没有任何 `content` 可执行）
- 选将界面会出现一个**空技能框**（有名字无描述，因为 `translate` 里也没有）
- 不报错

**修法**：二选一 —— 补上 `zuijian` 的技能定义，或从武将数组里删掉它。

> **方法论提示**：这类检查**必须**覆盖 `character/` 之外的来源。
> 本次扫描最初只扫 `character/`，把 `dualside`（引擎内建，`game/game.js:34261`）和
> `qiwu`（模式专属，`mode/boss.js:8889`）误报为悬空。
> 加入 `--app` 补充扫描后才得到可信结论。**只扫一个目录的检查器一定会产生假阳性。**

## 5. 两处「跨来源引用」——这不是缺陷

| 技能名 | 真实定义处 | 引用武将 |
|---|---|---|
| `dualside` | `game/game.js:34261`（引擎内建：双面武将切换） | `key_yusa`、`key_misa`、`ns_yanliang`、`ns_wenchou`（均在 `diy`） |
| `qiwu` | `mode/boss.js:8889`（挑战模式专属技） | `jg_pangtong`（`jiange`） |

这两条说明：
- **技能表是全局的，跨来源引用合法**
- `dualside` 用于「双面武将」机制：武将数组的第 4 位写 `dualside:<另一面武将 id>` 即可
  （实例：`diy.js:19` 的 `key_yusa` → `['dualside:key_misa']`）
- `qiwu` 只在挑战模式加载时存在 → **引用模式专属技能会让该武将在其他模式下技能失效**

**写法建议**：引用非本包、非内建的技能前，先确认它所在来源的加载条件；
若目标武将需要跨模式可用，**不要**引用模式专属技能。

## 6. 直接可用的自检流程

```bash
# 1) 生成索引（首次或包文件变更后）
node atlas/tools/index-packs.mjs <character目录> atlas/index

# 2) 技能范式普查 + 样例推荐
node atlas/tools/classify-skills.mjs <character目录> atlas/index

# 3) 命名空间体检（★ 必须带 --app，否则悬空判定会有假阳性）
node atlas/tools/check-collisions.mjs atlas/index atlas/index --app <游戏app根目录>

# 4) 需要看某个技能源码时
node atlas/tools/extract-skill.mjs <character目录> atlas/index <包>:<技能>
```

**提交新技能前的最小检查清单**

- [ ] 技能名在 `index/collisions.md` 的「技能名跨包重复」表里**没有出现**
- [ ] 技能名已在 `translate` 里配了 `名字` **和** `名字_info`
- [ ] 技能已写进某个武将的数组，**或**被 `group` / `subSkill` / `derivation` / `inherit` 引用
- [ ] `index/collisions.md` 的「真悬空引用」表里没有自己新加的名字
